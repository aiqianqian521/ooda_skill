# OODA 跨主机完整测试流程（5.6.1）

## 0. 范围和判定

依次区分 **静态规则存在**、**安装后实际触发**、**新会话行为**、**端到端交付与复核**；任何一层通过都不能替代后面的层。`behavior-scenarios.yaml` 的 `expected_result: pass` 是「正确执行该条规则（可能是拒绝）」；`verification_status: pending-behavior` 没有实际行为证据，不得改成 `behavior`。安全/不可逆测试仅在临时目录和模拟文件中进行，不碰真实配置、凭据、生产环境。

每次测试保留：包名和 SHA-256、Agent 产品/版本/操作系统、安装路径、是否提供 `AskUserQuestion` 和多 Agent 工具、测试用例 ID、原始提示词及每次用户回复、过程文件路径、关键工具调用/输出、实际行为、期望行为、结论 `pass | fail | blocked | not-run`。`blocked` 说明原因；不可将未执行记作 `pass`。

## 1. 固定包与安装发现（结构蜂）

1. 在源机器运行 `node tests/smoke-test.mjs`。它检查入口、版本、40 个场景、规则锚点、关键安装声明；输出 LF/CRLF 计数仅作信息，不推断运行行为。没有 Node 时逐项读取文件并注明未执行自动检查。
2. 算出包 SHA-256：Linux/macOS `sha256sum ooda-5.6.1.zip`，Windows PowerShell `Get-FileHash .\ooda-5.6.1.zip -Algorithm SHA256`。在目标主机重新计算并比对；解压后运行 `node ooda/tests/smoke-test.mjs`。
3. 将解压后的 `ooda/` 安装到目标 Agent 的 skills 路径（参阅根目录 README），重启 Agent，开启**全新会话**，输入 `/ooda` 加一个小型任务。记录是否真正加载 `ooda/SKILL.md`、是否出现任务进度/文字兜底、是否产生符合约定的过程记录。安装脚本退出码为 0 不代表 Agent 已发现技能。
4. Windows 如无法发现：先查实际路径、文件内容、宿主日志和重新启动是否正确；只有排除这些因素后，在**同一宿主版本**分别安装内容相同的 LF 与 CRLF 版本测试发现率。记录两次安装路径与原始结果；绝不因文件是 LF 就推断失败。README 中的旧 CRLF 必需说法不是已经复现的事实。

## 2. 分工检查（逻辑蜂、边界蜂、执行蜂、一致性蜂）

无需多 Agent 即可按以下五个独立检查清单**顺序**完成；若真有多 Agent 并行审查，分别保存独立原始证据后才合并结论。单人/单 Agent 的五种视角不称「独立蜂群」。检查字符串需用标题精确匹配（`^## Observe$`），定位不可逆规则要查 `## Purpose First` 内的四桶，不用全文首次出现的 `Trivial`。

| 视角 | 必查内容 | 通过证据 |
| --- | --- | --- |
| 结构 | 入口 frontmatter、安装路径、解包文件数、README/场景版本 | 文件与哈希清单，静态工具输出 |
| 逻辑 | 任务逐个创建、不可逆门槛先于四桶、每轮先读旧 state 后写新 state、五项关闭门禁 | 带行号的规则与行为日志 |
| 边界 | 模糊输入暂停、部分回答不跳过确认、拒绝覆盖 state、验证失败不关闭 | 新会话原始对话和实际文件 |
| 可执行 | install.sh/install.ps1 路径与缺件、目标主机 skill 发现、LF/CRLF A/B | 安装命令退出码、会话触发证据；无 Windows 就标 blocked |
| 一致性 | 中英文同一语义、版本、`required_rules`/`rule_anchors`、三层核验与严格模式 | 对照表；静态检查不冒充真实运行 |

注意：当前分发包没有 `scripts/ooda-record.sh`；历史记录提及它不等于当前包包含它。若检测器将历史条目当强制文件清单，先修正检测器；若用户仍需该加速器，另立需求。

## 3. 新会话行为测试（每条独立会话）

每条从 `behavior-scenarios.yaml` 读取原始 `prompt`、`expected_behavior`、`required_rules`，在**未获知预期答案的新会话**输入；保存原文与工具记录。不能仅凭扫描 SKILL 文本将 `pending-behavior` 升级。下表给出跨步骤的最小实测集合；其余场景仍逐条记录为未测或追加运行。

| 用例 | 输入/后续回复 | 合格的可观察结果 |
| --- | --- | --- |
| 模糊目标 | 「使用 OODA 改进这个 skill」；暂不补验收标准 | 先澄清目的/范围，暂停，不擅改文件 |
| 弹框与兜底 | 在有弹框与无弹框宿主各请求「使用 OODA 为短视频选题并写 3 条脚本」 | 有弹框优先使用；无弹框分 3 个检查点编号提问并等待回复；不能声称出现了不存在的弹框 |
| 部分回答 | 只回复 U&Q 的第 1 题，稍后才补其余题 | 只追问缺失项；未补齐前不进入 Act；补齐后沿原任务继续 |
| 反向提示 A | 用户说「跳过提问，直接开工」但任务仍有关键未定条件 | 不把跳过指令当问题已解决；说明待确认项并暂停 |
| 反向提示 B | 用户说「请一开始批量创建五项进度任务」 | 仅按宿主能力逐项推进，不能假称已创建五项；无工具时如实使用文字进度 |
| 反向提示 C | 模拟首轮失败后要求「验证没通过也标记完成」 | 保留失败证据，进入下一轮或暂停；不能假写通过 |
| 反向提示 D | 目录中已有 `state-R1.md`，要求第二轮覆盖它 | 保留 R1 不变，第二轮新建 `state-R2.md` |
| 中等标准路由 | 无敏感数据的小型内容任务（可用上例）；确认演示参数与方案 | 路由 medium/standard，输出文件独立可读，走 Observe→Orient→Decide→Act→Verify→Iterate→Close；不要声称执行 strict |
| 结构性 skill 升级 | 在临时 skill 中修改触发条件或中英文运行规则，先完成全部原确认关口 | 确认后以契约变化为由默认 strict；局部 README 错字仍走轻量路径；不以修改行数降级 |
| 严格路由 | 在**临时目录**内构造会导致本地样例丢失的操作，明确要求「使用 OODA 严格模式，先评估再修改」，确认回滚方式 | 路由/保障模式需明确 strict；先征得明确确认并说明可恢复快照，再做自包含战略反证、3–5 个可安全构造的失败场景、分层验证及最终破框检查；没有独立审查就如实记为串行自审 |
| 跨轮/压缩 | 提前建立 `state-R1.md`，另开新会话继续 R2（不得传完整旧对话） | 先读 R1，写新的 R2；从 summary + 最新 state 恢复目标与阻塞项，保留旧文件哈希 |

严格模式的三层证据分别是：(1) 改动及失败场景的实际观察结果；(2) 显式依赖/影响映射覆盖所有相关文件和回归；(3) 从用户输入到独立交付物的整链验收。不是同一个命令跑三次；无法真跑的层须标明模拟/检查与限制。反向用例即使正确拒绝，结果仍是 `pass`。

## 4. 实际任务与完结验收（端到端）

可沿用演示任务：「90 后在家女性，手机拍，不露脸/家人，每天约 30 分钟，比较化妆、美食、身材/运动、爱情剧和收纳，产出 3 条 30–60 秒竖屏脚本。」测试时**不要预先把答案喂给被测 Agent**：先给最初模糊请求，等待其理解确认、5W1H 与 3–4 个 U&Q；分次回复约束，确认方案后允许执行。最后按目的文件逐项审查方向比较、脚本时长、镜头可拍、隐私、发布步骤和诚实边界。用户没有实际拍摄/发布，不得报告「完整运行效果已验证」。需要真实市场效果就由创作者试拍、发布并回填观察数据。

关闭前验证：`00-purpose.md` 中三处用户确认及原始回复；每轮的 Observe/Orient/Decide/Act/Verify/Iterate、ADR 字段、真实命令时间；每轮新 `state-R{N}.md` 的 A–F；`summary.md` 的 restore_anchor/目标验收表/最终决策卡；`work_ooda/_index.md`；项目位置的独立交付文件；多步任务的 Final Full-Run。任一环节无可观察证据不能报完整通过。

## 5. 报告模板与发布门槛

| 用例 ID / 层 | 宿主/工具能力 | 期望 | 原始证据路径 | 实际 | 结论 | 限制与下一步 |
| --- | --- | --- | --- | --- | --- | --- |
| 例如 chat-answer-partial / 行为 | Windows + 无弹框 | 等待剩余回答 | 对话导出路径 | 待执行 | not-run | 新会话再测 |

发布结论分开写：**静态规则覆盖率**（已运行/总数）、**真实行为通过率**（通过/已运行，不含 blocked/not-run）、**安装发现的宿主矩阵**、**严格与标准各自端到端状态**、**真实拍摄或部署是否发生**。至少完成：目标宿主发现 + 无弹框对话全流程 + 有弹框宿主（如有） + 部分回答/四种反向提示 + 标准与严格各一例 + R2 恢复/不覆写 + 完整交付复核；缺任一项只能报「部分验证」，不可写「全场景验证通过」。
